# ADR-X1002: Provider SPI is separately versioned Experimental capability protocol 1.1.0

Status: Proposed/Experimental R11 implementation candidate. The controlled host protocol versioning, every-`Error` terminal rule, and current-X6 selection guard await a fresh r11 independent review. Earlier X1 r10 and X1/X5/X9 integration evidence is historical only and does not approve this R11 candidate.

## Context

X0 reserves a fourth compatibility axis for controlled provider ABI/capability negotiation. Existing v1 descriptor extensions are intentionally not retained or executable, and existing API SemVer, asset Profile, and adapter-target compatibility cannot imply provider ABI compatibility.

## Decision

X1 places controlled provider contracts in `com.liy.blendlib.spi.experimental`, marks them with `@ExperimentalBlendLibSpi(protocol = "1.1.0")`, and uses existing canonical `BlendResourceId` identities with bounded version ranges. `1.0.0` remains historical initial capability data-plane metadata; it does not select a legacy host throwable policy. `CapabilityRegistry` stays generic and deterministic with metadata-only `register -> discover -> freeze` behavior, priority-descending/provider-id-ordinal reporting, explicit duplicate identity/highest-priority tie errors, required fail-close, and optional predeclared safe fallback diagnostics. A current X6 generation is deliberately narrower: before generic discovery it intersects every caller request with `[1.1.0, 1.2.0)`, then rejects a frozen selected offer outside that current line. Therefore a broad caller request cannot silently choose a historical `1.0.0` offer into the current X6 lifecycle. Registration first safely captures and validates the provider identity, then reserves both that canonical ID and the exact provider object for one monotonic operation epoch before invoking `offers()` or acquiring its iterator. A registered or reserved same ID therefore returns CAP-001 without running the contender's offer callback; different IDs may collect metadata concurrently. Only a fully copied, validated immutable offer list commits atomically. Every ordinary, terminal, or traversal failure releases only its exact reservation, so a later retry cannot remove a newer reservation or observe partial publication. Reservation cleanup reads the current stored token, compares its primitive epoch, and only then removes the key; boxed `Long` value identity is never used as the cleanup predicate. Plans/selections are registry-produced rather than publicly constructible and bind exact provider identities to frozen offer snapshots.

`ProviderLifecycleSession` carries only a frozen generation plan and selected provider instances through prepare/apply/publish/retire/shared close. A valid plan proves exact source-registry identity, that registry's private one-shot freeze event, exact frozen-plan object identity, and exact equality with the registry's independently retained private freeze generation in addition to retaining the full request and exact provider-object/offer snapshot; every lifecycle entry independently recomputes and validates all provenance/selection/binding invariants, with bounded CAP-016 rejection before ownership or callbacks. Provider offer collection acquisition/traversal is single-pass, count-bounded, and normalizes containable caller failures to CAP-013 without trusting their diagnostic. Capability-request traversal likewise reserves an epoch, executes once outside the registry monitor, is bounded to 1,024 entries, commits only after epoch revalidation, and reports invalid/failed input as CAP-017. A single X1 identity policy limits canonical provider/capability/adapter identities to 256 code units, and invalid diagnostic identities are omitted. Failure normalization never invokes untrusted exception message or string conversion.

Registry metadata, request traversal, provider lifecycle, adapter registration, and provider close use explicit two-phase operation epochs. External callbacks run outside owner monitors; nested calls are rejected by a callback marker and racing calls by the active operation/epoch. Callback completion revalidates epoch, state, plan provenance, and object identity before committing. Ordinary non-`Error` `Throwable` failures become fixed bounded diagnostics and cleanup occurs in `finally`; every `Error` is terminal and is rethrown as the same original object only after new operations are stopped, adapter/registration state is detached where applicable, terminal state is recorded, and every ownership handle is released exactly once. Terminal prepare/apply keeps the session transition active and state `RETIRING` through release/close; it publishes `CLOSED`, the final immutable diagnostics, and the original `Error` to one bounded completion before clearing the transition. That completion remains the only terminal observation source after it is complete: initiator, concurrent, and later `retire()`/`close()` callers receive the same `ProviderLifecycleResult` instance or rethrow the same original `Error`. Callback reentry is rejected before an observer could await itself. Adapter install rollback and terminal adapter cleanup consume every ownership-release result: original terminal primary wins and suppresses secondary cleanup; terminal cleanup wins over an ordinary primary and suppresses it; two containable failures are retained in one bounded diagnostic. Rollback keeps the operation active through close, preventing early reattach, and ends it before any selected failure is propagated. Thus reentrant prepare/apply/publish/retire/close or adapter install/register/uninstall cannot publish a provider already retired/closed, overwrite a nested adapter, leak a handle, remain permanently busy, or deadlock merely because a callback waits for another thread. Interruption/timeout is explicit CAP-008. A pin lease prevents both generation retire callbacks and ownership release until snapshot users release their generation; after the last drain the order is retire then shared-owner release/close. Weak identity-keyed ownership spans overlapping generations and platform control; the final release marks the provider terminal before one close attempt, so failure is not retried and a closed instance cannot be reacquired. It never runs discovery or backend switching in hot paths.

## Alternatives rejected

- Treating v1 descriptor extensions as a provider payload: conflicts with accepted descriptor retention/rejection boundaries.
- Selecting equal top priorities by discovery order: nondeterministic and unreviewable.
- Leaving provider selection mutable after publish: violates generation/snapshot safety.
- Exposing raw renderer/platform handles: prevents adapter evolution and violates pure API boundaries.

## Compatibility impact

This is explicitly not stable facade ABI. A historical `1.0.0` provider may remain visible to generic data-plane tools but must advertise the current compatible line before current X6 use; it cannot recover an earlier containment interpretation by negotiation. Future breaking provider changes require a new capability protocol/ABI decision and migration path. This change modifies no existing stable facade signature, stable error code, descriptor, Profile, wire payload, adapter JAR contract, or release Gate.
